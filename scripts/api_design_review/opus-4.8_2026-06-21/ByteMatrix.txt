API Design Review — ByteMatrix

All findings verified against source.

1. OVERALL ASSESSMENT
A clean, mature specialization that conforms closely to the IntMatrix baseline and the narrow-integer tier
(Byte/Short/Char). Factory, accessor, diagonal, update/replace, transform, reshape/resize/extend, stacking,
arithmetic, conversion, zip, stream, and forEach families are internally consistent, correctly validated, and
honestly documented. Byte sign/overflow — the highest-risk area for this type — is handled exemplarily: the
class Javadoc and each of add/subtract/matmul/updateAll/map/zipWith document modulo-256 wrapping, the cast vs
implicit-narrowing distinction, and the widen-first remedy via toIntMatrix()/toLongMatrix(). Conversions are
complete for the convention (toInt 2753, toLong 2778, toFloat 2822, toDouble 2866). There are no
class-specific correctness or design defects; ByteMatrix's only items are participation in family-wide gaps.

  > Verified by grep: no toByteMatrix/toShortMatrix/toCharMatrix exists on ANY class. The family convention is

    widening edge, but short is not a conversion target anywhere, so ByteMatrix is CONSISTENT. (The Wave-2
    agent flagged this as a High missing-method; verification against the actual convention rejects it.)

at the family level.
  > Byte/Short/Char all lack primitive mapTo* (consistent tier), but they DO expose toXxxMatrix converters, so
    a mapToInt would pair naturally. Low priority because the absence is uniform across the narrow tier.
